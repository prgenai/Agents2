Section 1: Core Mechanics & Problem Space

Autonomous AI agents execute code, make network calls, and access sensitive data—often with the same permissions as their human operators. Traditional guardrails based on prompts and behavioral fine-tuning aren't reliable enough for enterprise use. OpenShell fixes this by enforcing security at the OS kernel level, creating an isolation boundary that no compromised agent can escape. Think of it as a sandbox for AI: constrained permissions, monitored actions, and out-of-process policy enforcement.

Why Prompts and Guardrails Aren't Enough

Large language models are powerful tools, but they're also unpredictable. Ask an agent to analyze customer financial data, and it seems simple. In practice, it's risky. The agent has to generate code, make API calls, read files, and talk to databases. If something goes wrong—if the model gets jailbroken, if a prompt injection slips through, or if there's a bug in the agent framework—the damage can be immediate and severe.

Current defenses try to prevent this at the application layer:

  • Prompt-based guardrails tell the agent not to access sensitive data
  • Behavioral fine-tuning teaches the model to follow safety guidelines
  • Allowlists in the code specify which APIs the agent can call

The problem is simple: these are soft boundaries. If the agent is compromised or the model misbehaves, there's nothing stopping it from reading a private key file, exfiltrating customer data, or making unauthorized API calls. The OS gives it permission to do all of those things.

The Sandbox Model: OS-Level Enforcement

Modern web browsers solve this problem with sandboxes. Each tab runs in its own process with restricted permissions. Even if a tab is compromised, the browser's sandbox prevents it from breaking into other tabs or accessing your entire system. The OS kernel enforces the boundary—no JavaScript on the page can override it.

OpenShell applies the same principle to AI agents. Instead of asking the agent to follow security rules, the operating system enforces those rules on the agent's environment. The agent can't make arbitrary network calls, read arbitrary files, or execute arbitrary processes—the kernel intercepts these actions and checks them against policy first.

This is a "deny by default" architecture. The agent gets only the specific permissions it needs. Everything else is blocked at the kernel level.

If the agent is compromised, it doesn't matter — the Gateway still enforces the rules.

Three Layers of Kernel Enforcement

OpenShell uses three independent kernel-level enforcement mechanisms. Each one is a separate layer, so compromising one doesn't compromise the others:

Layer 1: Landlock LSM (Filesystem Isolation)

Landlock is a Linux kernel security module that restricts filesystem access. Think of it as a per-process allow-list for files and directories.

OpenShell uses Landlock to lock down the agent's filesystem view:

  • Everything outside /sandbox and /tmp is read-only, so the agent can't modify system files
  • The agent can read and write to /sandbox (its working directory) and /tmp (temporary files), but nowhere else
  • These restrictions are enforced at the kernel level—no userspace code can override them

This means even if the agent is compromised and gains shell access, it still can't read config files, modify binaries, or access other users' data.

Layer 2: seccomp BPF (System Call Filtering)

seccomp stands for "secure computing." It lets you write rules that filter which system calls a process can make. If the process tries to make a forbidden call, the kernel kills it or blocks the call.

OpenShell uses seccomp to restrict dangerous operations:

  • Blocks system calls that could escape the sandbox: ptrace (for debugging), mount (for mounting filesystems), clone with the CLONE_NEWUSER flag (for creating new namespaces)
  • Allows safe system calls: reading and writing files, making network calls, spawning processes
  • If the agent tries to escape, the kernel silently denies the system call or terminates the process

This provides defense against privilege escalation: even if the agent finds a kernel vulnerability, it can't exploit it if the necessary system calls are blocked.

Layer 3: HTTP CONNECT Proxy + OPA (Network Policy)

The third layer controls network access. All outbound connections flow through a proxy controlled by the gateway.

The proxy uses Open Policy Agent (OPA) to enforce network policies:

  • Before the agent can connect to an external API, the proxy intercepts the request
  • OPA checks if the destination IP/hostname is on the allow-list
  • Only approved connections are allowed through; everything else is blocked
  • The proxy can also strip headers, redact PII from the request, or log it for audit purposes

This prevents data exfiltration: even if the agent is compromised, it can't talk to unauthorized endpoints.

Walking Through a Request

Here's what happens when an OpenShell agent tries to do something:

  1. The agent generates a request (e.g., "fetch data from the company database").
  2. That request hits the first enforcement layer: Landlock checks if the agent is allowed to access the files it needs. If it's trying to read /etc/passwd, Landlock blocks it immediately.
  3. The request moves through seccomp: if the agent tries to make a forbidden system call (like ptrace), the kernel kills the process.
  4. The request reaches the HTTP proxy: if the agent is trying to connect to an external API, the proxy checks the policy. Only whitelisted endpoints are allowed through.
  5. The Privacy Router strips credentials from headers, redacts PII from request bodies, and logs the action for audit purposes.
  6. The sanitized request goes to either a local model (Ollama, vLLM) or a cloud model (Claude, GPT-4). The response comes back through the same router.
  7. If the agent tries to connect to an unauthorized endpoint, all three layers reject it: Landlock blocks file access, seccomp blocks the system call, and the proxy blocks the network connection. The attempt is logged and can trigger an alert.

The key insight is that all three layers work independently. Compromising one layer doesn't grant access to the others. This is true defense in depth.

YAML Policies: Defining the Rules

Administrators define what the agent can and can't do in a simple YAML file. Here's an example:

name: financial_analyst_agent spec: filesystem: allow_dirs: - /sandbox/data - /tmp deny_patterns: - /etc - /home - /root network: allow_hosts: - api.company.internal - claude.anthropic.com - api.openai.com deny_hosts: - "*.external-service.com" processes: allow_binaries: - /usr/bin/python3 - /usr/bin/curl - /usr/bin/jq privacy: strip_headers: - Authorization - X-API-Key redact_patterns: - SSN: "\\d{3}-\\d{2}-\\d{4}" - CreditCard: "\\d{16}"

The policy is declarative, not imperative. Administrators say what's allowed; everything else is denied. This follows the principle of least privilege: agents get only the specific permissions they need to do their job.

Section 2: Financial Agentic Workflows

Financial services are OpenShell's killer application. Compliance requirements like KYC, AML, and SOX demand that sensitive data is handled carefully. OpenShell lets finance teams deploy AI agents to analyze data, generate reports, and make recommendations while maintaining strict compliance. Every action is logged, every network call is filtered, and PII is automatically redacted.

Use Case 1: KYC/AML Compliance Analysis

Scenario

A bank's compliance team receives a new customer application. It includes documents, transaction history, and identification information. The team is short-staffed and processing applications manually would take days per application.

Traditional Approach

Hire more compliance staff or build a custom ML model. Both are expensive and slow.

OpenShell Solution

Deploy an AI agent inside OpenShell to analyze applications automatically. The agent can:

  • Extract structured data from documents (names, addresses, transaction amounts)
  • Check transactions against AML watchlists
  • Generate risk assessment reports
  • Flag suspicious patterns for human review

OpenShell ensures that:

  • The agent can only read the specific files it needs (the customer's application)
  • It can only connect to the AML watchlist API, not arbitrary external services
  • All PII (SSNs, passport numbers, account numbers) is automatically redacted from logs and audit trails
  • Every action is logged for compliance audits

Result: Processing time drops from 2 days to 20 minutes per application. Compliance risk is actually reduced because every action is monitored and auditable.

Use Case 2: Regulatory Reporting

Scenario

A brokerage firm needs to submit quarterly regulatory filings (10-Q, 10-K) to the SEC. The filings require aggregating data from multiple systems, reconciling discrepancies, and formatting according to strict rules. This typically takes weeks and requires careful human review.

OpenShell Solution

An agent pulls transaction data from the firm's trading systems, asset management platform, and accounting system. It performs reconciliation, applies regulatory rules, and generates the filing in the correct format. The Privacy Router redacts internal pricing information before the report is sent to regulators.

Guarantees:

  • The agent can only read data from approved internal systems (not the internet)
  • It can only write to the SEC filing API
  • Proprietary information is stripped before submission
  • Every data access and submission is logged with timestamps and user attribution

Outcome: Filing time shrinks from 3 weeks to 3 days. Accuracy improves because the agent runs consistent validation rules. Regulatory confidence increases because the entire process is auditable.

Use Case 3: Fraud Detection

Scenario

A credit card processor needs to detect fraudulent transactions in real time. Current rule-based systems catch obvious cases but miss sophisticated schemes that require contextual analysis.

OpenShell Solution

Deploy an AI agent that analyzes each transaction against historical patterns, merchant categories, geography, and risk signals. The agent can make decisions in milliseconds and flag suspicious transactions for deeper review.

Security guarantee:

  • The agent can only access the transaction stream and customer history database (predefined tables)
  • It cannot query external services or databases
  • Card numbers and sensitive account details are not exposed to the model—only anonymized transaction features
  • The agent's decision logic is logged and explainable for audit purposes

Benefit: Fraud detection improves by 40% while maintaining full auditability and compliance. Customers experience fewer false positives because the agent's decisions are more nuanced.

Section 3: NemoClaw Security Integration

NemoClaw is a production framework that uses AI agents for complex workflows in high-risk environments. OpenShell provides the security layer that makes NemoClaw safe for enterprise use. NemoClaw agents run inside OpenShell's sandbox, where their filesystem access, network calls, and process execution are monitored and controlled at the kernel level.

What is NemoClaw?

NemoClaw is an open-source framework for building resilient, multi-step AI workflows. It's designed for long-running tasks like data pipeline orchestration, document processing, and complex decision-making.

Key features of NemoClaw:

  • Multi-step workflows with retry logic and error handling
  • Tool calling and function composition
  • State persistence across steps
  • Integration with multiple LLM providers

But NemoClaw itself doesn't enforce security. It assumes the agent runs in a trusted environment with trusted models. That's where OpenShell comes in.

NemoClaw + OpenShell: A Powerful Combination

When you run a NemoClaw agent inside OpenShell, you get:

  • Filesystem Protection: The agent's file operations are intercepted and checked against policy before they happen. It can't read config files, private keys, or other sensitive files.
  • Network Isolation: All network calls go through the proxy. Only whitelisted endpoints are reachable. This prevents data exfiltration and command-and-control attacks.
  • Process Constraints: The agent can only spawn processes from a whitelist. It can't execute arbitrary binaries or shell commands.
  • Complete Audit Trail: Every step of the workflow is logged. You can replay the exact sequence of events that led to a particular outcome.

Security Interception Points

NemoClaw agents interact with the system at three main points. OpenShell intercepts all of them:

1. Network Policy (HTTP CONNECT Proxy)

NemoClaw agents make API calls to fetch data, invoke other tools, and talk to LLM providers. OpenShell's proxy inspects all these calls:

  • Checks the destination IP/hostname against the allow-list
  • Inspects headers and request bodies for credential leakage
  • Redacts PII before the request leaves the sandbox
  • Logs the call with timestamps and outcome

2. Filesystem Policy (Landlock LSM)

NemoClaw agents read files (data files, config, model weights) and write files (logs, results, intermediate state). Landlock controls these operations:

  • The agent can read from /sandbox (its input data) and write to /sandbox (its output)
  • System directories (/etc, /usr, /lib) are read-only or inaccessible
  • The agent can't modify binaries or system configuration

3. Process Execution (seccomp BPF)

NemoClaw can spawn subprocesses (to run tools, invoke scripts, execute binaries). seccomp controls which processes are allowed:

  • Only whitelisted binaries can be executed (e.g., /usr/bin/python3, /usr/bin/curl)
  • Privilege escalation attempts are blocked (ptrace, setuid)
  • Dangerous system calls are forbidden (mount, clone with CLONE_NEWUSER)

Step-by-Step: What Happens When a NemoClaw Agent Tries to Access Something

Scenario 1: Allowed Access

  1. NemoClaw agent needs to fetch customer data from an approved internal API.
  2. The agent calls the API endpoint (e.g., api.company.internal/customer/123).
  3. The HTTP proxy intercepts the request. It checks if api.company.internal is on the allow-list. It is.
  4. The proxy examines the request headers and body. There are no exposed credentials (the Privacy Router stripped them).
  5. Filesystem policy (Landlock) checks if the agent is allowed to cache the response. It can write to /sandbox, so it's allowed.
  6. Intent verification confirms the access pattern matches the policy.
  7. The request is sent to the API. The response comes back and is stored in /sandbox. The action is logged.

Scenario 2: Blocked Access

  1. The agent is compromised and tries to send customer data to an external service (attacker.com).
  2. The agent initiates a network connection to attacker.com:443.
  3. The HTTP proxy intercepts the request and checks the allow-list. attacker.com is not approved.
  4. The proxy blocks the connection and logs the violation.
  5. An alert is sent to the operator console with details: timestamp, agent ID, destination, attempted action.
  6. The operator can investigate the logs to understand what happened and whether the agent was compromised.

Risk Assessment

No system is risk-free. Here are the main risks to consider:

Kernel Vulnerabilities: OpenShell relies on the Linux kernel's security modules (Landlock, seccomp). If a kernel vulnerability is discovered in one of these modules, OpenShell's security could be compromised. Mitigation: Keep your kernel up to date, subscribe to security advisories, and have an incident response plan.
Policy Misconfiguration: If policies are written too loosely (e.g., allow-listing too many endpoints), the sandbox loses effectiveness. Mitigation: Use policy templates, code review for policy changes, and automated testing of policies.
Zero-Day Exploits: A sophisticated attacker might find a way to exploit a combination of kernel vulnerabilities, policy gaps, and application flaws to escape the sandbox. Mitigation: Assume sandboxes can be broken. Design your system so that even if an agent escapes, it can't cause catastrophic damage. Use additional defenses (network segmentation, rate limiting on APIs, alerting on unusual patterns).
Operational Overhead: Managing policies, monitoring logs, and responding to incidents requires skilled staff. Mitigation: Invest in automation (policy templates, automated alerting, incident playbooks). Consider managed OpenShell services if you don't have internal expertise.
